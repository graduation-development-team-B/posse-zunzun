# 問題仕様と成果物

## 問題形式・回答形式

この仕様と`docs/quiz-formats.md`を読む。対応済み機能は後者を正本とする。以下は会話で採用された形式の整理であり、アプリの実装済み機能一覧ではない。後の変更がある場合は最新のユーザー指示と元資料を照合する。

| 問題形式 | 回答・入力 | 主な採点対象 |
|---|---|---|
| 選択式 | 単一選択・複数選択・○× | 選択した回答 |
| プレビュー＋コーディング式 | 穴埋め・トークン組み立て・部分編集・自由入力 | HTML構造、スタイル、操作後の状態。必要ならConsoleも確認 |
| コーディング式 | 穴埋め・トークン組み立て・部分編集・自由入力 | JavaScriptのConsole出力・関数の戻り値 |
| ターミナル式 | コマンド・操作の入力。問題で許す補助入力を明示 | ファイル・Git等の最終状態、学習目標に必要な操作履歴 |

行の並べ替えとPRのbase/compare等の操作シミュレーションは元資料では候補。対応が確認されるか、ユーザーが採用するまで必須問題として作らない。トークン組み立てと行の並べ替えを同じ機能として扱わない。

実行環境はHTML/CSS/DOMのプレビュー、Web用React、JavaScript実行、Git/Linuxシミュレーター等を問題別に記載する。新しいバックエンドや採点システムの実装を問題制作から派生させない。

## week冒頭に記載すること

- 対象phase/week、問題数、対象者の既習範囲。
- 参照ファイルと節。取得できる場合はソースのGitリビジョン等も残す。
- weekの学習目標、ミニドリルで必要な判断、問題への対応表。
- 4つの支援対象と問題形式の内訳。無理に全項目を使わない。
- 独立・連続の構成、実行環境、教材の不整合などの前提。

## 各問題に必要な項目

### 作成者向け情報

| 項目 | 内容 |
|---|---|
| 問題ID | phase/weekと問題を識別できる安定したID。既存問題の改訂では不用意に変更しない |
| 版 | 初版・改訂を識別できる値。既存の版管理があれば従う |
| 主なつまずき | 言葉の理解／知識の選択／知識の組み立て／結果の確認・修正の一つ |
| 学習目標 | 「分かる」だけで終えず、判断・説明・編集など観察可能な行動で書く |
| 教材の根拠 | インプットのファイル・節、必要に応じて行番号。未確認の出典を作らない |
| ドリルとの対応 | 対象問題・作業・判断を具体的に記載。直接対応がなければ前提知識としての関係を記す |
| 既習知識 | 解答と問題の読解に必要なもの。固定コードの説明との区別も書く |
| 形式 | 問題形式と回答・入力方法を別々に記載 |
| 概念・類題 | 概念ID、類題グループ、元問題との変更点。類題がなければその旨 |
| 依存関係 | 独立なら「なし」。連続なら前提ID、引継ぎ内容、復習用の開始状態 |
| 検証 | 実行済み／静的確認のみ／要確認、実施内容、未確認部分 |

### 学習者向け内容

1. **問題文**：目的・現在の状態・求める回答。必要なら期待結果や操作条件。
2. **提示物**：コード、入力値、選択肢、見本等。画像に依存するなら素材パスと確認済みの内容。
3. **初期状態**：編集するファイルやシミュレーターの開始状態。
4. **編集範囲**：変更できる部分と固定部分。必要な修正が許可範囲内で完結すること。
5. **達成条件**：学習者が結果を照合できる、観察可能な条件。
6. **ヒント**：考える着眼点。必要な場合に開ける内容として分離。
7. **解説**：回答後に示す、正答の理由・主要な誤答の理由・教材の参照先。

選択式の初期コードや編集範囲など、該当しない項目は「該当なし」とする。全形式に架空のコードやテストを付けない。

### 採点者向け内容

- 正答・模範実装。複数の正解がある場合は許容範囲を示す。
- 判定条件と必要な入力・操作・期待結果。
- 採点上の不合格例と、その例で確認する条件。
- 学習者に表示する未達条件やエラーの説明。
- 実行結果と回答コードが同じ版であることなど、採点に必要な前提。

## 形式別に落としやすい条件

### 選択式

- 単一選択は条件下で正解が一つであること。
- 複数選択は複数選択であることを明示し、完全一致・部分点の採点方針を記す。
- ○×は一つの明確な命題を問う。暗黙の環境や曖昧な「必ず」に依存しない。
- 誤答の理由を一つの可能性として扱い、選択だけから学習者の理解状態を断定しない。

### プレビュー＋コーディング式

- 初期ファイル、編集可能範囲、ランタイム、依存関係を明記する。
- 画面幅・入力・クリック等、判定に必要な条件を指定する。
- スクリーンショットの完全一致だけで採点しない。構造・スタイル・状態等の達成条件を分ける。
- Reactの警告等、見た目だけで判断できないものはConsoleやコード上の条件も使う。

### コーディング式

- 入力と期待出力・戻り値、出力形式や比較方法を定義する。
- 小さな問題の範囲で、必要な通常ケース・境界ケースを用意する。
- 正答実装の検証に加え、狙った誤実装を判定できることを確認する。

### ターミナル式

- 作業ディレクトリ、ファイル内容、ブランチ等の開始状態と到達状態を定義する。
- 許可コマンドとシミュレーターの対応範囲が不明なら要確認として扱う。
- 複数の有効な操作列を許す。操作履歴自体が学習目標のときは別途条件を示す。
- 実環境・外部リモートへの変更を問題の動作検証として勝手に実施しない。

## week末尾のレビュー記録

問題IDごとに、出典確認、正答確認、主要な誤答確認、実行検証の状態を短く記す。静的レビュー済みと動作検証済みを分ける。未確認問題を完成数に混ぜて全問検証済みと報告しない。

最後に、教材の矛盾、未対応形式、環境不足など残る事項を示す。残件がなければ「要確認事項なし」と記す。
