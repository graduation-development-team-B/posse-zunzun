# posse-zunzunへのクイズ制作・実装フロー移行計画

作成日：2026-10-06

目的：既存クイズと制作・検証の仕組みをposse-zunzunへ引き継ぎ、以後は同リポジトリ内で、対象Weekの制作からアプリ表示・採点・記録まで進められるようにする。

この文書は計画。移行・アプリ改修はまだ実施していない。最初の動作確認対象はWeb版を暫定推奨とし、iOS・Androidも初回対象とする場合は実行環境の工程を拡張する。

## 1. 調査して確認できた現状

### 移行元：posse-quiz

- アプリ：Expo 54。
- 問題の正本：`content/PH1/questions.json`。問題本体とauthor情報を保持。
- 単元・用語・Git模擬操作の正本：`content/PH1/catalog-base.json`。
- 問題数：Week01〜06各12問、Git/GitHub10問、合計82問。
- 現行内訳：選択式・候補選択式64問、HTMLトークン4問、JavaScript Console4問、Git/PR模擬操作10問。
- `scripts/build-ph1-content.js`が配信用JSONと単元別Markdownを生成。AI APIの呼び出しはない。
- `scripts/validate-fixture.js`、問題契約・採点・実行テスト、検証記録がある。
- HTML表示はWebのiframe。ネイティブ版CodePreviewは案内表示のみ。ConsoleはブラウザWorker。
- 採点はローカル。自由入力・React実行・サーバー採点等は今回82問の対応範囲に含まれていない。
- 現在は未コミットの変更が多数ある。GitのHEADだけからコピーすると、今回作成した問題・スクリプトを取り落とす。

### 移行先：posse-zunzun

- アプリ：Expo 57、React Native 0.86.3。旧版のUI・API依存をそのまま持ち込めるとは判断しない。
- `src/data/drill.ts`にWeek一覧、問題、結果、進捗などのモックがまとまっている。
- `src/app/quiz.tsx`は固定の選択問題、`src/app/build.tsx`は固定のHTML組み立て問題。
- `options.tsx`はweek/count/typeを渡すが、quiz画面はその指定で問題を選んでいない。
- 現在の遷移はquiz→build→doneが固定。ヘッダー件数と結果も固定。
- build画面のプレビューはReact Native要素による模擬表示。学習者のHTMLを実行するプレビューではない。
- 作問データ、カタログ生成、問題検証、学習セッション・永続保存の基盤は見つからなかった。
- Week05・06がWeek一覧にない。GitのIDは`git`、通常WeekのIDは`w01`等で、移行元と異なる。
- 調査時点でmainにコミットがなく、ファイルは未追跡。実装開始時に既存ファイルのスナップショットを確保する。

## 2. 引き継ぐ方針

### コンテンツ

- 82問の本文・正答・誤答理由・解説・出典・ヒント・作成根拠を引き継ぐ。
- 既存の問題ID・単元ID・問題の版を保持する。旧UIのw01等は境界の対応表で変換し、データを都度改名しない。
- 通常は各Week10〜15問、独立問題、1問の主対象は4分類のうち一つ、という制作方針を引き継ぐ。
- 旧コンテンツのpublished/deleted状態も保持。新規制作ではdraft→reviewed→publishedの制作状態を追加し、未確認問題を公開候補へ混ぜない。
- 正本は一つ。配信JSONとレビュー資料は生成物として扱う。

### アプリ

- posse-zunzunの画面・配色・マスコット・操作の見た目に接続する。
- 移す実装は純粋な採点関数、トークン操作、Gitシミュレーターなどを優先する。UI、ストレージ、ブラウザ実行コードは依存を調べて接続する。
- 現行82問が必要とする入力・実行・採点を移す。仕様文書にある未実装の形式まで、移行の完成条件に自動追加しない。
- 解説の教材リンクは教材の該当箇所へ接続する。現在の/materialsはWeek選択画面なので、そのまま教材リンクとして流用しない。リンク未整備の間は出典を表示する。
- 実行と回答確定を分ける。編集後は実行結果を古いものとして扱い、再実行するまで確定できない。
- ヒント利用を記録し、自力正解とヒント利用後の正解を区別できるようにする。

### 制作フロー

- curriculumとdrill-ph1は教材の参照元として維持する。
- 作問仕様と手順をposse-zunzun内へ置き、通常の制作でposse-quizを読みに戻る必要を減らす。
- 学習者向け教材の操作指示・AI禁止等は教材内容として扱い、作成エージェントへの命令と区別する。
- 制作スキルは旧リポジトリへの固定参照を解消する。まずリポジトリ内の手順を正本にし、個人インストール済みスキルはそこを参照する薄い入口に更新する。

## 3. 移行後の配置案

```text
posse-zunzun/
  content/
    units.json                         # 単元・順序・対応形式
    PH1/
      catalog-base.json                # 用語・Git模擬操作等
      weeks/
        week01.json                    # 問題 + author情報
        week02.json
        ...
        week06.json
        git-github-level1.json
  scripts/
    build-content.js                   # 配信JSON・Markdown出力
    validate-content.js                # 型、参照、出典、件数、対応機能の検査
  src/
    data/generated/catalog.json        # アプリが読む生成物
    types/content.ts
    lib/content/                       # 読み込み・UI用の変換
    lib/quiz/                          # 採点、トークン、実行、セッション
    lib/progress/                      # 回答履歴・途中状態の保存
    components/drill/                   # 既存UI + 問題形式別の表示
  docs/
    quiz-authoring.md                   # 1Weekの制作から投入までの手順
    quiz-formats.md                     # 対応済みの問題・回答形式
    quiz-contents/                     # 自動生成の確認用資料
    migration/                         # 移行対象一覧・比較結果
  tests/content/
```

既存questions.jsonのWeek分割は機械的に行い、問題の内容・順序・IDを比較する。将来は1Weekのファイルを編集するだけで制作できるようにする。単元一覧・件数の検証はunits.jsonから導き、対応Weekや総数82を複数のコードへ固定しない。

作者情報のすべてを学習画面へ渡さず、ヒント・主対象・版など画面と記録に必要な項目を生成時に明示して選ぶ。現行のローカル採点では正答データも端末に含まれる。この移行だけで正答の秘匿が実現したとは扱わない。

## 4. 実装順序と完了条件

### 第1段階：移行元を確定し、作問基盤と82問を取り込む

作業：
- 両リポジトリの最新状態を再確認し、既存ファイルを保護する。
- 未コミットの実ファイルから、コンテンツ・スクリプト・仕様・検証対象を一覧化。ハッシュを記録する。
- content、型、生成処理、制作手順、必要なテストを移す。旧アプリ全体の依存は持ち込まない。
- Week別の正本へ変換し、配信用カタログとレビュー資料を生成する。
- 単元登録と対応形式の設定を用意する。

完了条件：
- 全82問とGitの全stageが欠落せず、ID・本文・正答・解説等の意味が保持される。
- Week01〜06各12問、Git10問で、移行元との比較が通る。
- 新リポジトリから生成・検証コマンドを実行できる。
- 制作手順は新リポジトリと教材だけを参照して完結する。

### 第2段階：選択式を実データに接続し、1セッションを完成させる

作業：
- Week一覧をカタログから生成し、Week05・06とGitを表示する。
- week/count/typeから出題する問題ID列を一度確定し、再描画で変わらないセッションを作る。
- quiz画面へ64問の選択式・○×・候補穴埋め・バグ診断を接続。コードがある問題はコードを表示する。
- 回答→誤答別の説明・共通解説・ヒント・出典→次問→結果を実データ化する。
- 途中回答、確定状態、回答履歴、ヒント利用を保存し、再起動後に復元する。
- 保存はプラットフォームごとの実装を境界で切り替えられる構造にする。
- 当該Week・形式の問題数が3/5/10問より少ない場合は、選択可能件数を示して開始する。生成済みの問題総数と1回の学習件数を分ける。

完了条件：
- 例えばWeek03・5問・選択式の指定で、該当する5問が表示され結果まで進める。
- ヘッダー、正誤、件数、結果、学習進捗がそのセッションと一致する。
- 再開・二重確定・入力なし・存在しないID・出題可能問題0件を処理できる。
- 表示のクリア条件は明文化する。暫定案は「当該単元の全公開問題に一度以上正解」。ヒント利用は別に記録し、クリア表示を実装力の保証としない。
- XPは既存の表示案を踏まえて付与条件を定め、確定イベントごとに一度だけ反映する。

### 第3段階：HTML・JavaScript・Git/PRを接続する

作業：
- 問題の形式とpreview/console/activityRefから適切な表示へ振り分ける。
- build画面の固定問題・模擬表示を、4問のHTMLトークン問題と実プレビューへ置き換える。
- JavaScript4問のコード・Console・実行結果判定を接続する。
- Git10問のトークン・ログ・状態・PR操作を接続する。
- 現在のchoice/buildという選択肢を、利用可能な問題形式に対応させる。少なくとも「おまかせ」と形式別の選択を検討し、未対応形式を黙ってスキップしない。
- mixでは単元内の対応済み全形式を扱い、連続問題の前提を必要としない出題にする。

Web先行の場合：
- HTMLはiframe、ConsoleはWorkerを版に合わせて移す。
- Native向け画面でも利用可否を明示し、Web用機能が動くように見せない。
- iOS・Androidの実プレビュー・JavaScript実行は次の段階で実装・検証する。

初回からiOS・Androidを含む場合：
- Expo 57の公式資料に沿ってネイティブの表示・実行環境と依存を選ぶ。
- コード・実行ID・出力・エラー・終了・キャンセルを扱う共通契約を設計する。
- プレビューとJavaScriptをプラットフォームごとに実装し、実機確認を完成条件へ追加する。
- WebのWorker/iframeをネイティブへ直接移せると見積もらない。

完了条件：
- 82問すべてが対応形式で表示・入力・採点できる。
- HTML/Consoleは未実行と編集後の古い結果で確定できない。
- JavaScriptの通常・境界入力、エラー、キャンセルを検証する。
- Git/PRは各stageを独立した開始状態から完了できる。
- 選択→実行形式→選択のような混在セッションが完了・復元できる。

### 第4段階：ここで新しいWeekを作る運用を完成させる

制作手順：
1. 対象Week・問題数・既習範囲・利用可能な形式を指定する。
2. 対象のインプット・ドリルから「概念→必要な判断→練習する問題」の対応表を作る。
3. 10〜15問をdraftで作る。本文・正答・誤答理由・ヒント・解説・出典・4分類を記録する。
4. 自動検証で件数、必須項目、参照、ID、対応形式、採点・実行を確認する。
5. 教材との意味の照合、既習範囲、正答の一意性、誤答理由をレビューする。
6. 指摘された問題だけ修正し、reviewedへ進める。
7. 公開対象を選んでpublishedにし、カタログ・Markdownを生成する。
8. 代表問題の画面と1セッションを確認する。

コマンド案：
- `content:build`：正本から配信用JSON・Markdownを作る。
- `content:validate -- --week week7`：対象単元の検証。
- `test:content`：問題・採点・実行契約の検証。
- `typecheck`、`lint`：アプリ変更がある際の必須確認。

完了条件：
- 未作成の1Weekを試し、教材参照→draft→修正→公開→アプリ確認までこのリポジトリ内で通せる。
- 選ぶ対象Weekは別途指定する。計画段階でWeek07以降を生成しない。
- 既存対応形式であれば正本と単元設定の追加で出題できる。新しい実行環境が必要な形式は、対応機能を先に実装・検証する。
- 件数・分類・検証状態・未確認事項が単元ごとのレビュー資料から分かる。

## 5. 検証の分担

| 検証 | 確認すること |
|---|---|
| 移行比較 | 82問のID・内容・正答・版、Git stageの欠落がない |
| 形式・参照 | 件数、重複、必須項目、単元・概念・活動参照、実行機能の対応 |
| 教材の出典 | ファイル・見出し・行・ハッシュを確認し、教材変更時に再レビューへ戻す |
| 採点・実行 | 全候補の正誤、HTMLトークン、JS出力、Git操作、古い実行結果の拒否 |
| セッション・保存 | 指定範囲、順序、件数、次問、途中再開、二重記録防止、版の違い |
| 画面 | 実データの表示、コード、ヒント・解説、プレビュー、誤答・結果 |
| 人・AIによる意味の確認 | 未習知識、曖昧な条件、複数正答、誤答理由、ミニドリルとの接続 |

既存の正答IDとの一致テストだけでは教材上の正しさを保証しない。静的レビューと実行検証の状態を区別する。学習記録には問題IDと問題の版を残し、改訂で過去の回答を別の問題の回答として解釈しない。

## 6. AI消費を抑えるための運用

- 通常の作問依頼は1Week単位。対象教材・関連ドリル・仕様・既存の良問数例を入力にする。
- 教材の読解と問題制作はまずSolで試す。モデル・設定は制作担当側で選ぶ。
- Astraの確認は曖昧な条件、未習事項、コード実行の判定、解消しないレビュー指摘などへ絞る。
- 件数、JSON整形、参照検査、Markdown出力、実行結果検査はスクリプトで行う。
- 修正は問題IDごとに行い、AIで全Weekを書き直さない。生成物の再出力はスクリプトに任せる。
- 作問ルールと対応機能をリポジトリ内へ固定し、毎回の設計議論・旧アプリ全体の探索を減らす。
- 1Weekの試行で修正回数・完成品質・実際の消費を確認して分担を調整する。

次回の依頼例：

```text
docs/quiz-authoring.mdとdocs/quiz-formats.mdに従って、PH1の指定Weekを12問作成してください。
対象Weekのcurriculumと関連するdrill-ph1を参照してください。
各問に出典、既習範囲、4分類、正答・誤答理由、ヒント、解説を付けてください。
対応済みの形式を使い、Week別の正本を編集してください。
検証・生成を実行し、未確認事項を報告してください。
新しい入力・実行機能が必要な問題は要確認として提示してください。
```

## 7. 最初の実装単位

最初は「作問基盤と82問の取り込み＋選択式の1セッション」を完成させる。この時点で制作・確認の置き場所がposse-zunzunに移り、既存問題を使ってデータ接続を検証できる。その後、残る実行形式を接続し、新しい1Weekの制作で運用を確認する。

計画書は現在の仕様リポジトリに保存した。実装時に新リポジトリのdocsへ置き、以後の改訂先もそこで統一する。
